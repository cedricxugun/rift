把“吞噬”做进 BUILD

Wanderburg 最值得借鉴的是分层的模块成长、会推进的候选池和载具属性分工。我们的下一步应把吞噬事件、武器分支和城堡形态连在一起，让不同构筑产生不同操作选择。

研究对象：H:\gamequ\Wanderburg Game · 包内版本 EA 0.9.14.1。下文的 V6 内容均为设计提案，当前可玩 Demo 仍为 V5.1。

证据口径：从 IL2CPP 元数据恢复类型与字段，结合原生指令反汇编核对关键分支，再解码序列化配置。恢复的 C# 声明中存在空方法体，它们不等于原始源码。本轮没有把实际游玩作为证据，也没有对整套运行时行为作完整验证。

一、直接从代码确认的设计

1. 升级有两条不同的轴：成长类型与品质

ModuleUpgrade.UpgradeType分为冷却、自动攻击、主动技能、传奇、特殊五类；RarityValueCount = 4对应另一条四档数值品质轴。传奇是成长节点类型，不能直接理解为“所有卡里的第五档品质”。Module2还分别记录自动、主动、冷却等级及已安装升级。

一个主模块的配置结构节点数用途
自动攻击路线5强化基础输出，可附加范围、弹速等属性
主动技能路线5强化主动效果、弹量、持续时间等
冷却路线5改变触发频率
两组 A/B 特殊分支4改变攻击机制
A/B 传奇分支2提供互斥的后续方向

20 个主模块各有 21 条配置，共 420 条；7 个乘员模块合计 38 条。大量内容来自“同一套结构承载不同效果”，不意味着需要手写几百种完全独立技能。

证据：ModuleUpgrade.cs、Module2.cs；game-configurations.json 中 458 个 ModuleUpgrade 实例。包内包含备选和预制体，数量不代表所有节点同时可抽。

2. 候选池是一条会推进的路线

ModuleSelection.AdvanceUpgradePool的原生分支确认：先移除已领取项，再把它配置的后继节点加入候选池；排除已安装和重复项，并检查模块 ID。传奇选择还会移除对应的另一条传奇项。抽选代码会调用ArtifactSystem.IsArtifactEligibleForCurrentBuild；代码里存在装备条件、构筑标签与候选不足时的补位处理。

本地配置的新模块机会位于内部等级 3、12、24，说明“获得新武器”和“强化已有武器”有独立节奏。经验需求前十项为 30、50、70、85、100、110、120、130、140、150，后续封顶为 500。这里只说明配置，不能直接把这些数值移植到我们不同的资源产量和地图尺寸里。

本地场景配置提供 1 次初始升级重抽、2 次初始神器重抽。幸运值经过单独的权重函数处理；序列化表中的默认概率不应直接当成最终实际概率。

3. “吞”和“打”确实各有职责

Harvester.CanPlayerAbsorbAgent先排除不可吸收、盟友、已吸收、已死亡／已回收及生命失效的对象；车辆交给AgentVehicle.CanCurrentlyBeAbsorbedByPlayer检查。普通单位比较玩家体型等级，车辆比较单独的“可吞车辆等级”。该入口没有“必须先打至某个生命百分比”的通用条件；其他状态仍可能影响可吞资格。

// 依据已核对分支归纳的伪代码；不是恢复出的原始 C#。
if (!有效敌人 || !可吸收 || 是盟友 || 已死亡或回收) return false;
if (敌人是车辆) return 敌人吞噬等级 <= 玩家可吞车辆等级;
return 敌人吞噬等级 <= 玩家体型等级;

这支持我们原来的设想：成长应使旧威胁变成食物，同时让更大的目标保留战斗价值。黑洞吞噬可以成为一种处决、补充战斗资源和触发连锁的操作。

这些配置的可吞车辆等级从 0 升到 3，主动槽容量都为 4。包里另有 3 套命名不同的基础参数，使用路径未确认，因此不能把“15 套参数”说成“15 种载具”。这些速度使用对方引擎单位，不能与我们当前 6.4 的速度直接比较。

可借鉴的是三种职责：耐打、收集、机动。手机上应继续采用直接拖动移动，把这些差异做进底盘与技能，避免把转向惯性变成操作负担。

5. 填充属性也有实际作用范围

侧炮自动攻击的一个升级配置同时包含基础伤害调整、四档追加伤害 [0, 6, 9, 15]，以及可选的范围／弹速属性。另有模块尺寸、模块速度、行驶状态影响攻击、连续使用不同技能返还冷却等独立实现。

例如AbilityComboRefund对应的本地配置要求 3 秒内使用 3 种不同技能，配置了 0.2 的冷却返还系数。这是“操作方式影响组合效果”的一个例子；最终应用范围仍需结合调用路径确认。界面里的弹速、召唤物移速、载具移速必须明确区分。

6. 刷怪采用多层计划，地图也有任务

WaveSpawner同时包含常规池、中立单位波次、预编排波次、群袭、Boss 与加时阶段。刷出位置还检查地图边界、与玩家距离和屏外位置；按帧限制批次生成。草地、沙漠、暗林各有三套地域配置，难度、任务与收益倍率分别配置。

一个初期阶段预制体配置 Boss 时间 240 秒、加时开始 420 秒，这只是该预制体的局部阶段参数，不能当成整个游戏统一时长。它说明了“阶段”和“整局”需要分开设计。

三、V6 提案：三条有操作差异的吞城路线

以下为我们的原创设计建议先做三条能完整成型的路线，再扩展数量。建议同时装备最多 3 个主武器与 1 个核心；替换武器时展示损失与返还，避免让玩家误以为刚才的升级消失。

风暴炮港

拆解 → 回收 → 连射

炮击拆出碎片；吞碎片积攒装填进度；完成一轮回收后获得下一轮强化齐射。

分支：重型穿透炮 / 散射回收炮。一个擅长破盾，一个擅长清理与续航。

外观：长炮管或宽口多联炮；风帆和装填灯随状态变化。

熔炉吞城

点燃 → 吞噬 → 喷发

吞下燃烧中的小敌人积攒炉压；满炉压自动喷出火雨，玩家通过接近目标加快爆发。

分支：持续燃烧地带 / 瞬时连锁爆破。燃烧、范围与吞噬效率形成闭环。

外观：炉门变亮、烟囱喷火；爆发前有清楚的蓄压反馈。

霜镜庭院

冻结 → 吞噬 → 护卫冰片

吞下冻结目标获得环绕冰片；冲刺时释放冰片，主动选择保留防御还是打出扇形攻击。

分支：控制护航 / 碎冰追击。避免单纯把冰系变成另一种伤害颜色。

外观：温室冰冠、可数清的护卫冰片和冲刺扇形轨迹。

吞噬与战斗的统一规则

目标建议规则玩家获得什么
食物与碎片尺寸满足即可吞基础成长、技能能量；部分构筑获得额外循环资源
低一级的普通敌人可以健康状态直接吞明确感受到旧威胁变成食物
同级重甲敌人先破甲，再接近吞噬；危险阶段给清晰图标比远处击杀更好的构筑资源回报
精英与 Boss满足阶段／破绽条件后才能整吞有仪式感的收尾与进化奖励

体型、可吞等级和受击核心分开管理。城堡长大后提高吞噬能力，中央受击区域保持清楚。吞噬触发的爆破、回血、消弹都设置冷却和次数上限，防止连锁无限递归。

让随机性提供选择，也提供可控性

  • 每次三选一优先提供：已有路线推进、另一种机制选择、通用数值或生存能力。已经选掉的互斥分支不再出现。
  • 关键机制节点保证有获取机会；品质主要改变数值或附加词条，避免成型完全依赖高品质运气。
  • 给少量免费重抽；候选不足时有清晰的治疗或资源补位。解锁新蓝图后允许调整本局候选范围，避免内容越多越难凑 BUILD。
  • 每个选项显示“现在 → 选择后”，包括实际弹数、冷却秒数、范围、适用武器。属性只对当前真正使用它的系统投放。

保留十分钟成长，但用阶段目标填满它

建议阶段主要体验应观察的结果
0–2 分钟学习吞噬，拿到第一种明显改变攻击的升级能够判断自己在走哪条路线
2–5 分钟争夺营地／车队，完成首个机制分支探索收益与迎战风险形成选择
5–8 分钟组合生效，新敌人克制当前操作习惯已成长的玩家能轻松处理旧敌人
8–10 分钟完成核心，进入一段清晰的爆发体验玩家有时间使用成型 BUILD
10 分钟以后Boss 多阶段检验；胜利后可选继续挑战额外挑战自愿进入，并明确风险与奖励

敌人强度按每阶段预期成长设计。强化远程怪的数量、攻击重叠和屏外预警应比单纯加血量更优先控制。不能让玩家刚升级，就立刻用等比例加血抵消成长收益。

局外养成继续小幅提升，并开放新的路线

底盘、装甲、回收、补给四项改装保留上限。后续奖励以新底盘、起始模块和分支蓝图为主；新蓝图先允许试用。失败有稳定收益，关键操作手感在零改装状态下也应成立。不要把慢移速、少恢复或无效属性设计成必须长期付出时间才能修好的缺陷。

四、实施顺序与验收条件

顺序具体改动验收条件
P0：构筑结构新增技能节点图、标签、互斥分支和候选池推进；拆开品质、类型、等级相同武器能形成两种可识别打法；不会抽到失效词条；领取不会重复结算
P1：吞战闭环先实现上面三条路线的吞噬触发效果，接入破甲提示、蓄能和动作吞敌与远处击杀会导致不同决策；一眼能看出爆发来源；连锁有上限
P2：地图与压力阶段目标、资源点和威胁预算；成型后留出爆发阶段中期不是空地图绕圈；屏外远程攻击有预警；失败原因可以复盘
P3：长期目标底盘、蓝图试用与可控候选范围，调整零件获取新解锁提供新策略；解锁越多不会明显降低成型可靠性

代码落点：数据层增加 skill-graph.js 与节点条件；game.js负责候选推进、吞噬事件和奖励事务；arsenal.js订阅吞噬／破甲／冲刺事件；renderer.js表现可吞状态与蓄能；ui.js展示分支取舍与前后数值。工坊和现有单文件离线构建继续沿用。

数值验证先使用同种子对照：记录前 2 / 5 / 8 分钟的选择次数、已形成机制、受伤来源和恢复供给。自动驾驶用于验证流程，真人试玩用于判断手感。性能用持续移动与后期组合场景复测，沿用 V5.1 的像素预算。
